# Machine and acquisition files

Every TestbenchDAQ command combines exactly two JSON documents:

```text
machine.json + acquisition.json -> one resolved session configuration
```

This makes experiments portable without allowing an experiment file to change
where a machine writes data or how it reaches installed hardware.

## `machine.json`: one installed acquisition host

`machine.json` uses schema `testbenchdaq/machine/v1`. It is local, untracked,
and normally created once from `machine.example.json`.

It owns values that describe the machine, not a measurement:

| Section | Examples | Why it belongs here |
| --- | --- | --- |
| Root | `machine_name`, `output_root` | Identifies the host and its approved storage location. |
| `gator` | native binary/library paths, device index, timeouts | Depends on the installed Gator runtime and USB topology. |
| `endaq` | serial, model, mount path, command/remount timeouts | Protects recorder identity and Linux mounting behavior. |

Do not commit this file. Do not place its values in a GUI-generated experiment
or share it with another bench without deliberately adapting it.

## `acquisition.json`: one measurement definition

`acquisition.json` uses schema `testbenchdaq/acquisition/v1`. It is portable
and may be generated by the Lager-Testbank TestDesigner. It owns:

| Section | Examples |
| --- | --- |
| Root | `name` |
| `schedule` | start delay, window duration, count, start-to-start period, late-start policy |
| `gator` | enabled state, channel, sample rate, full scale, threshold |
| `endaq` | enabled state and the explicit enabled/rate choice for every channel |

Use one acquisition file per meaningful test definition. Its contents should
be enough for someone to understand what was measured, while the session
manifest remains the record of what actually occurred.

## Create and validate a pair

```bash
cp machine.example.json machine.json
cp acquisition.example.json bearing-baseline.acquisition.json

.venv/bin/tbdaq \
  --machine machine.json \
  --acquisition bearing-baseline.acquisition.json \
  show-config
```

`show-config` is the safe first check: it validates both documents and prints
the resolved configuration without commanding hardware.

## Scheduled windows

A session can contain one or many acquisition windows. A short diagnostic test
is simply one window; repeated diagnostic checks and long degradation tests
are both scheduled-window sessions. `run_period_s` is measured from one
planned start to the next, so it must include measurement duration and device
cleanup. On Lager-Testbank, the GUI also enforces its enDAQ recovery allowance
between stop and next start commands.

## enDAQ channel choice

The example acquisition profile lists every known S3-E100D40 channel with an
explicit `enabled: false`. Change only the channels you intend to record to
`true`. The sample-rate limits and supported-rate lists are there to make a
valid choice visible; TestbenchDAQ verifies the selected configuration against
the connected recorder where the device exposes that information.

Inspect the recorder before creating a profile for another recorder model:

```bash
.venv/bin/tbdaq --machine machine.json \
  --acquisition bearing-baseline.acquisition.json endaq-info
```

## Local service and GUI

The localhost service uses only the protected machine file. The Lager-Testbank
GUI sends an acquisition request derived from its experiment plan; it cannot
override output storage, mounted-device identity, or installed executable
paths. See [local service and GUI integration](../engineering/local-service-and-gui.md).
